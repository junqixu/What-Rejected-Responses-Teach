# Repository audit for rebuttal implementation

Audit date: 2026-07-26. Target tree: `D:\codex`.

## 1. Current repository summary

The checkout is a small collection of standalone research scripts rather than a
packaged application. Top-level entry points are `sft.py`, `eval_vllm.py`,
`eval_final.py`, and `eval_answer_passk.py`. Preference generation and DPO
training live under `dpo/`; PPO/GRPO experiments live under `ppo/`; datasets are
stored under `data/`.

The `.git` directory in this workspace is empty, so `git status`, commit, branch,
and remote provenance cannot be recovered. This must be fixed in the execution
environment before any formal result is considered fully traceable.

## 2. Existing perturbations

| Capability | Verified location | Audit result |

The new `rebuttal/taxonomy/base.py` therefore provides a conservative trace
parser and deterministic graph-edit adapters. It returns “not applicable” when
an edit cannot be structurally located; it does not pretend to recover the
paper's unavailable source DAG.

## 3. DPO trainer and log-probability reduction

Existing full-parameter entry points are `dpo/full/dpo.py` and
`dpo/full/dpo_train.py`; the LoRA entry point is `dpo/lora/dpo_train.py`. All use
TRL `DPOTrainer` directly. None overrides `get_batch_logps`, so standard DPO uses
summed response-token log-probabilities. Paths and most settings are hard-coded.

The scripts disagree with the requested shared setting: observed learning rates
include `2e-5`, `1e-5`, and `5e-6`. The new `rebuttal/train_dpo.py` isolates the
rebuttal runs, defaults to one epoch, effective per-process batch size 8,
learning rate `5e-6`, beta `0.1`, and `sum` reduction, and adds an explicit
`mean` control. It supports `--max_samples`, `--dry_run`, and output collision
protection.

## 4. Diagnostic preference entry point

No chosen-vs-rejected diagnostic preference evaluator exists in the checkout.
`eval_vllm.py` and `eval_final.py` evaluate generated final numeric answers only.
This is a blocking gap for isolated A/B/AB diagnostic accuracies until model
checkpoints and a scored-pair evaluator are added.

## 5. Reasoning@k evaluator

`eval_answer_passk.py` computes numeric answer pass@k for k in 1, 8, 16, and 32
and reports OP buckets. It does not implement Reasoning@k and does not use a
reasoning correctness evaluator. Calling its output “Reasoning@k” would be
incorrect.

## 6. Actual JSON schemas

The 3-way generated preference datasets contain:

```text
chosen, d, error_type, id, length, mode, op, prompt, rejected,
source_problem, source_question, template
```

Counts in `data/dpo_outputs/` are 673 computation, 461 dependency mismatch, and
946 missing-node records. `data/yzh_data/dpo_missing_nodes_414.json` contains 414
records with the same schema. `data/full/validation.json` is JSONL despite its
`.json` suffix and contains 3,800 rows with:

```text
d, id, length, mode, op, problem, question, solution, template
```

Original records have no hashes, split, DAG metadata, edit location, severity,
or generator version. New generated records add all required manifest fields.

## 7. Checkpoints and loading

The intended initialization is hard-coded as
`/root/autodl-tmp/checkpoint/qwen2_0.5b_sft_op10/checkpoint-10339` in
`dpo/full/dpo_train.py`; another script omits the `checkpoint/` path segment.
Models load with `AutoModelForCausalLM.from_pretrained(..., device_map="auto")`.
The tokenizer is loaded separately from `Qwen/Qwen2-0.5B`. No checkpoint exists
inside this workspace, and no model/tokenizer revision is recorded.
